Shared State That Complicates It
These live at module level in app.py and are used across all route groups:
- limiter — Flask-Limiter instance, decorates routes in api and projects
- _load_whitelist / _whitelist_cache — used in before_request
- _make_oauth_session / _refresh_access_token / _get_valid_token — used by auth routes AND api routes (SDC writes need tokens)
- _csrf_token / _validate_csrf — used by every POST route across all blueprints
- login_required decorator — used by routes in every blueprint
- get_project_for_user / verify_image_ownership / has_sibling_match — DB helpers used by projects and api blueprints
- _download_image — used by api_manual_face and api_update_face_bbox
- commons_thumb_url / _snap_thumb_width / _THUMB_STEPS — used by projects, api, and pages
- _is_human_entity / _commons_category_exists / _fetch_p18_thumb_url / _fetch_wikidata_label — Wikidata/Commons API helpers used by project creation
- _remove_sdc_claim — used by api_reclassify
- Constants: MAX_BBOX_PX, MIN_BBOX_AREA, PROJECTS_PER_PAGE, MAX_IMAGE_DOWNLOAD_BYTES, OAuth URLs, etc.
All of this would need to move to a shared helpers.py or stay in app.py and get imported by each blueprint module.
Template url_for() Changes
Every url_for('function_name') in all 9 templates would need blueprint prefixes:
url_for('index')           → url_for('pages.index')
url_for('login')           → url_for('auth.login')
url_for('logout')          → url_for('auth.logout')
url_for('dashboard')       → url_for('pages.dashboard')
url_for('project_detail')  → url_for('projects.project_detail')
url_for('api_classify')    → url_for('api.api_classify')
...
That's ~50-80 url_for() calls across templates, plus any in Python code (redirects in route handlers).
Test Breakage
This is the biggest issue. The tests mock module-level attributes like:
monkeypatch.setattr(app_module, "_is_human_entity", ...)
monkeypatch.setattr(app_module, "get_project_for_user", ...)
monkeypatch.setattr(app_module, "_load_whitelist", ...)
monkeypatch.setattr(app_module, "_download_image", ...)
monkeypatch.setattr(app_module, "execute_query", ...)
If _is_human_entity moves to helpers.py and gets imported into blueprints/projects.py, the mock target changes. And due to Python's import system, you have to mock where the name is looked up, not where it's defined. So every mock path would need updating — potentially 200+ monkeypatch.setattr calls across 420 tests.
Some tests also import app_module directly:
import app as app_module
And then inspect its source code, check attributes, etc. Those would all need reworking.

Yes, you have plenty of room to scale up. The binding constraint is memory (4.5Gi free).
Current setup (from Procfile + jobs.yaml): web (gunicorn, 4 workers) + ml-worker (1 continuous job).
Options:
1. Bump worker concurrency (free, no extra pods) — increase MAX_CONCURRENT_PROJECTS and IMAGE_THREADS via env vars. You're at 3 projects × 4 threads = 12 concurrent image operations. Could go to 4×6 = 24 if CPU/memory allows. Just set WIKIVISAGE_WORKER_MAX_PROJECTS and WIKIVISAGE_WORKER_IMAGE_THREADS.
2. Run multiple worker instances — spin up a second ml-worker pod. Would need coordination to avoid double-processing the same project (current code doesn't have distributed locking, so this would cause duplicate work).
3. Increase gunicorn workers — currently 4 workers. Could bump to 6-8 if you're seeing web request queuing.
My recommendation: Option 1 is the easiest win — no code changes, just bump the env vars. You have the CPU headroom. Something like:
WIKIVISAGE_WORKER_MAX_PROJECTS: "5"
WIKIVISAGE_WORKER_IMAGE_THREADS: "6"
